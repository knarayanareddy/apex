# Apex review

## Scope and verdict

**Repository:** [knarayanareddy/apex](https://github.com/knarayanareddy/apex), pinned to `005c317609803fca6fd07511f7495562eb264fd1` on `main`. **Stage:** implementation with a substantial harness, supporting test projects, and preview/spec material; not an established production assurance assessment. The README calls it “production-grade” and promises “zero human intervention” ([README.md:3-5](https://github.com/knarayanareddy/apex/blob/005c317609803fca6fd07511f7495562eb264fd1/README.md#L3-L5)); those claims exceed this static review's evidence.

The strongest findings concern private-state validation and misleading migration verification reporting. Linux qualification succeeded historically at the reviewed SHA, but its success does not prove all threat boundaries or recovery. Runtime, tests, installs, builds, deployments, and project code execution were **NOT RUN** for this review. See [remediation plan](REMEDIATION_PLAN.md).

## Architecture and product boundary

The harness manifest exposes `pi-apex` through `bin/pi-apex` and requires Node 22.19 or newer ([package.json:6-14](https://github.com/knarayanareddy/apex/blob/005c317609803fca6fd07511f7495562eb264fd1/pi-apex-harness/package.json#L6-L14)). The sandbox constructs bubblewrap arguments; the cockpit exposes MCP, browser, PR and credential actions. CLI wiring was not traced. Private state includes sessions, SQLite/WAL and spills ([private-state-boundary.ts:1-8](https://github.com/knarayanareddy/apex/blob/005c317609803fca6fd07511f7495562eb264fd1/pi-apex-harness/src/core/private-state-boundary.ts#L1-L8)).

`consensus-cluster`, `metrics-pipeline`, and `brownfield-monorepo` have separate manifests and must not inherit the harness's qualification results. The metrics project depends on Redis; the harness depends on Pi packages, document parsers and native Linux facilities ([metrics manifest:6-12](https://github.com/knarayanareddy/apex/blob/005c317609803fca6fd07511f7495562eb264fd1/metrics-pipeline/package.json#L6-L12), [harness manifest:60-73](https://github.com/knarayanareddy/apex/blob/005c317609803fca6fd07511f7495562eb264fd1/pi-apex-harness/package.json#L60-L73)).

## Findings ledger

- **APX-01 — High, confirmed static: invalid topology can return from preflight.** [private-state-boundary.ts:51-57,138-150,159-193](https://github.com/knarayanareddy/apex/blob/005c317609803fca6fd07511f7495562eb264fd1/pi-apex-harness/src/core/private-state-boundary.ts#L51-L57) records stat failures in `violations` and sets `valid` from that array, but the validator never checks `report.valid`. If the device cannot be determined (`controlPlaneDev === null`) and neither symlink nor nested-mount condition fires, it returns an invalid report instead of throwing. Downstream impact depends on whether a caller checks the report; this was not traced. Fail closed on unknown topology and preserve diagnostic detail; test the actual preflight boundary.
- **APX-02 — Medium, confirmed static: dry-run verification is overstated.** [private-state-boundary.ts:346-380,387-440](https://github.com/knarayanareddy/apex/blob/005c317609803fca6fd07511f7495562eb264fd1/pi-apex-harness/src/core/private-state-boundary.ts#L346-L380) does not copy or hash files in dry-run, but returns `verifiedHashes: true`; it can set `integrityVerified` after checking only the source database. `sourceRetained` checks directory existence, not byte-for-byte retention. Operators may mistake a rehearsal for a verified restore. Distinguish not performed from passed and verify source/destination state when an actual copy is made.
- **APX-03 — Medium, confirmed static: browser comparison is intentionally one-shot, not a recurring gate.** [apex-browser-comparison.yml:3-14](https://github.com/knarayanareddy/apex/blob/005c317609803fca6fd07511f7495562eb264fd1/.github/workflows/apex-browser-comparison.yml#L3-L14) triggers only for workflow-file changes and requires one named branch with exactly 31 commits; its comment says “not a qualification gate.” Browser regressions cannot rely on this comparison running on ordinary changes. Decide the supported browser matrix and establish a separate repeatable gate; do not mistake this diagnostic for one.
- **APX-04 — Medium, unverified risk: metrics Redis may be exposed if the compose project is deployed beyond a trusted host.** [docker-compose.yml:2-8](https://github.com/knarayanareddy/apex/blob/005c317609803fca6fd07511f7495562eb264fd1/metrics-pipeline/docker-compose.yml#L2-L8) uses mutable `redis:7-alpine` and publishes `6379:6379` without an authentication option in the shown command. Actual host reachability, Redis configuration and production use are unknown. Treat this as a local test setup until deployment intent is decided; bind privately or remove publishing and verify any production authentication and image integrity.
- **APX-05 — High, unverified risk: privileged cockpit actions require end-to-end authorization proof.** [mission-control-server.ts:1534-1550,1620-1674,2280-2289](https://github.com/knarayanareddy/apex/blob/005c317609803fca6fd07511f7495562eb264fd1/pi-apex-harness/src/ring5/mission-control-server.ts#L1534-L1550) accepts an MCP command, PR test command and provider key. The server also writes pairing credentials with private directory and file checks ([lines 2384-2429](https://github.com/knarayanareddy/apex/blob/005c317609803fca6fd07511f7495562eb264fd1/pi-apex-harness/src/ring5/mission-control-server.ts#L2384-L2429)). Route-wide authentication, origin protection, trust boundaries, process confinement and credential redaction were not established. This is a priority validation, not a confirmed unauthenticated endpoint or injection exploit.
- **APX-06 — Medium, owner decision: isolation differs by operating mode.** [bwrap-sandbox.ts:49-53,243-253,417-433](https://github.com/knarayanareddy/apex/blob/005c317609803fca6fd07511f7495562eb264fd1/pi-apex-harness/src/core/bwrap-sandbox.ts#L417-L433) reports bubblewrap unavailable on macOS and has explicit `danger-full-access` and `allowUnsandboxedDev` paths. The default failure on unavailable bubblewrap is protective; an authorized override is deliberately unconfined. Define which platforms and modes may handle real repositories and secrets, rather than treating all modes as equivalent.

## Five-discipline assessment

**Correctness/code review.** APX-01 and APX-02 are source-level contract mismatches; exploitation and data loss were not demonstrated. Callers and recovery flows remain unsampled.

**Automation/testing.** The harness defines `test:canaries`, `test:neutral`, `test:linux`, `test:browser` and `test` ([manifest:16-18,34-38,52-53](https://github.com/knarayanareddy/apex/blob/005c317609803fca6fd07511f7495562eb264fd1/pi-apex-harness/package.json#L34-L38)). A [Linux qualification run](https://github.com/knarayanareddy/apex/actions/runs/41664502988) completed successfully at `005c317609803fca6fd07511f7495562eb264fd1`; this is historical CI, not an independently rerun result. APX-03 is a separate comparison-workflow limitation; it does not establish that other browser tests are absent.

**DevOps/operations.** The qualification workflow uses pinned checkout/setup actions, read-only contents permissions, disabled persisted checkout credentials, and locked install ([workflow:12-13,31-44](https://github.com/knarayanareddy/apex/blob/005c317609803fca6fd07511f7495562eb264fd1/.github/workflows/apex-linux-qualification.yml#L31-L44)). Private-state mounts, migration, restores, release provenance and nested-project deployments remain unobserved. APX-04 is conditional on use outside a trusted test host.

**OWASP/security.** Sandbox defaults include network unsharing, environment clearing, secret masking and fail-closed behavior for incomplete scans ([bwrap-sandbox.ts:289-297,346-385](https://github.com/knarayanareddy/apex/blob/005c317609803fca6fd07511f7495562eb264fd1/pi-apex-harness/src/core/bwrap-sandbox.ts#L289-L297)); effectiveness against races is unverified. APX-05 covers authentication/authorization, injection, credential handling and untrusted tool output. Dependency pins and lockfiles exist, but advisories, package provenance and artifact contents were not audited. Data retention, encryption and access controls for sessions, spills, and backups remain unknown.

**UI/UX/accessibility.** The cockpit is applicable; rendered UI, keyboard, screen reader and responsive behavior were not tested. Clearly distinguish confined mode, failed preflight and dry-run verification. No accessibility conformance is claimed.

## Production blockers and owner questions

Before real autonomous use, resolve APX-01 and APX-02, validate APX-05, and obtain an explicit platform/mode decision for APX-06. Who owns provider and GitHub credentials and approval scopes? Is the cockpit local-only, and is Redis merely a fixture? Which hosts provide persistent separate private-state storage, backups, restore access and signed releases? Who approves autonomous PRs, outbound network access and unsafe overrides? Release readiness and certification are not established.
