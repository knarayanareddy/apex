# Multi-format ingestion and export: harness review

**Reviewed:** 2026-10-27  
**Purpose:** Check whether the proposed Pi-Apex approach—separate, tested format adapters with bounded extraction, provenance and separate export generators—is consistent with current open-source agent practice. This is research only; no implementation change is authorized or made here.

## Executive conclusion

The adapter architecture remains sound, but this review found an important new candidate: **officeParser 8.3.0**, published on 2026-10-27. Its current Node/TypeScript package claims parsing for PDF, DOCX, PPTX, XLSX, HTML and more, with AST-based output to PDF, DOCX, PPTX, XLSX, HTML, Markdown and other formats. Its format coverage makes it a stronger first pilot than initially assumed. [officeParser npm](https://www.npmjs.com/package/officeparser) · [source repository](https://github.com/harshankur/officeParser)

Do **not** simply trust or embed it in the main server. Its own security policy says arbitrary document parsing has a large attack surface, hardening is best-effort, it is maintained by one person without a security team, and `abortSignal` cannot interrupt most parsers already running. It recommends isolation, externally enforced time/memory limits, `abortSignal`, and decompression limits. This means the candidate must first pass dependency/OSS audit, capability smoke tests, malicious fixture tests, and a killable restricted-process design. The newly released 8.3.0 also has little soak time. Pin the exact version; do not auto-upgrade or auto-install it. [officeParser security policy](https://github.com/harshankur/officeParser/blob/master/SECURITY.md)

The most relevant direct comparison is Hermes Agent: its documented `read_file` converts common formats into paginated readable text, with DOCX/XLSX available through its built-in path and PDF/PPTX/other formats using an optional converter. It imposes a size cap and explicitly documents scanned-PDF coverage warnings and OCR recovery options. That validates “format-aware extraction behind the ordinary file-reading interface,” while also showing why extraction quality, dependencies, and OCR fallback must be visible instead of pretending every page was understood. [Hermes document extraction](https://hermes-agent.nousresearch.com/docs/user-guide/features/document-extraction)

For complex layout/OCR, Docling is a useful optional backend rather than a harness feature: it supports PDF, DOCX, XLSX, PPTX, HTML and more, and exports a structured document representation plus Markdown/HTML/JSON/text-style outputs. Its breadth and layout capabilities come with a larger operational/dependency footprint. Its structured extraction exports are not the same as faithfully authoring a new DOCX/PPTX/XLSX; those need separate generators. [Docling formats and outputs](https://docling-project.github.io/docling/usage/supported_formats/)

## Recommended design for Pi-Apex

1. **Keep the core small; define a pluggable adapter interface.** E.g. `inspect(input)`, `extract(input, options)`, `export(document, format, options)`. Adapters return a normalized tree, not a flattened untraceable string.
2. **Keep extraction and authoring separate.** Initial ingest can produce a provenance-bearing internal document plus Markdown/text/JSON for model context. New output formats are separate generators: PDF, DOCX, PPTX, XLSX and HTML each need their own tests and layout/render validation. A parse/export tool that emits Markdown does not itself generate an Office deliverable.
3. **Start with deterministic adapters and narrow scope:** plain text/HTML; DOCX/XLSX/PPTX OOXML ZIP/XML extraction with compressed-size, entry-count and expansion-ratio bounds; PDF text-layer extraction with page-level provenance and explicit no-text/scanned-page warnings. Add OCR/layout backend later and only opt-in.
4. **Avoid auto-installing parsers.** Pin dependencies, expose installed capabilities in Settings/Doctor, and make optional heavy OCR explicit. A parser can process hostile ZIP/XML/PDF content; package presence is not a safety guarantee.
5. **Preserve provenance and uncertainty.** Each extracted segment should retain source file, page/slide/sheet, heading/cell range where applicable, extractor/version, truncation, OCR use, and warnings. Return excerpts on demand rather than injecting an entire long document.
6. **Use one bounded upload/selection path.** Validate actual file signatures as well as extensions/MIME, cap bytes/pages/sheets/entries/expanded bytes/time/memory, use private temporary files or confined descriptors, never execute macros/embedded scripts, and pass extracted content as untrusted data. Do not follow external links or download linked resources from inside a document without separate approval.
7. **Test by fixtures and failure modes.** Include corrupt/encrypted files, scanned and text PDFs, mixed orientation/tables, OOXML zip bombs and malformed XML, external relationships/DTD/entity attacks, large pages/sheets, Unicode, hidden text, prompt-injection content, limits, truncation, provenance correctness, and temporary-file cleanup. Verify no workspace/guardrail widening and no content persistence beyond normal transcript policy.
8. **Add format-specific output only with acceptance tests.** For document outputs, check they open with standard readers; validate page/slide/sheet structure, tables, images, metadata, fonts/fallback, and round-trip content. For PDF/PPTX visual quality, render in a local headless office/browser tool and test representative pages/slides.

## Bottom line

The proposal is better than extending the current image/audio attachment code into ad-hoc format branches: it gives parsers explicit resource/security limits and provenance, and keeps the public reader/exporter APIs separate. Research changes the library choice: **pilot `officeParser@8.3.0` first behind an internal adapter and a hard process boundary**, because its published format coverage matches the requested input/output scope and it fits Node 22. Do not adopt it as a main-process dependency until tests verify real outputs and the restricted worker contains parser failure. If the worker/capability audit fails, fall back to separate well-maintained per-format parsers or an optional Docling service; do not quietly remove limits or run hostile documents in-process. Hermes validates read-through and warnings; OpenHands validates the isolation/transfer boundary.
