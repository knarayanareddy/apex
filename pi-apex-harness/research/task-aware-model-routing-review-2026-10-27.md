# Task-aware model routing: feasibility and harness comparison

**Reviewed:** 2026-10-27  
**Question:** Should Pi-Apex route each submitted task to a different model/workflow, and how do the current build and other referenced harnesses do this?  
**Evidence rule:** Separate request-level model classification, phase-based model changes, agent-initiated delegation, explicit mode/action selection, and hosted-provider routing. These are not interchangeable. Product statements for closed systems are not evidence of their private implementation.

## Executive answer

**It can be done, but a generic “understand every prompt, choose model and workflow” router is not free.** It requires one of: (a) deterministic local rules (very little cost/latency, weak semantic understanding), (b) an extra classifier-model call (better semantic coverage, but adds a provider round-trip and cost), (c) an agent-initiated model/tool switch (only when the model chooses, potentially an extra call and not guaranteed), or (d) a hosted router with its own availability, pricing, privacy, and model-pool policies.

The clearest production example located is Cursor Router: it classifies each Auto request and selects from a managed model pool. Its classifier and routing system are proprietary; public docs do not quantify its added routing latency. An explicit phase alias such as Claude Code `opusplan` or Pi-Apex `apex/auto` is materially simpler: it chooses models by workflow phase, not by classifying each prompt. Many other tools expose Plan/Build/Act modes or let the main model delegate to a specialist; they do not document a mandatory per-request model classifier.

**Recommendation for personal Pi-Apex:** do not add an LLM classifier by default. The existing `apex/auto` already supplies a useful plan→implementation switch without a separate classifier call. First correct the confusing UI label and make that phase router easy to select. Keep browser/teamwork/schedule as explicit, reviewable workflow choices. Consider an optional per-request router only after measuring a real quality/cost problem that `apex/auto` plus explicit model selection does not solve.

## Pi-Apex: current behavior, precisely

- `src/ring6/provider-router.ts` implements `apex/auto`: each session branch starts on the configured planning model; after the first successful `edit`/`write` tool result it changes to the configured implementation model, with at most one phase transition per branch. This is **phase routing**. It does not classify the user’s request as simple, research, plan, browser, or schedule work before the first response.
- Ring 14's `src/ring5/task-mode-routing.ts` applies a local deterministic text-pattern heuristic as the user types. It provides a *suggestion*, not a semantic understanding. Selecting a task mode is manual. The separate “Use apex/auto for this session” action changes the session model before sending; it does not route the submitted request independently.
- The current UI's `Automatic — use the normal prompt` option means **no special task mode / preserve the current model**. It is not an automatic task classifier. This label is easy to misread and should be renamed if the design remains manual.
- `browser`, `schedule`, and `goal` use prompt framing; `teamwork` dispatches the existing `/swarm debate`; `plan` activates existing read-only Plan Mode. These are workflow actions, not model choices. Browser/tool use still depends on the model; the demo responder does not exercise it.

Therefore, the user’s proposed behavior—classify the complete submitted request and pick a route before task work begins—is **not implemented today**. `apex/auto` is useful but solves a narrower plan/execute transition.

## Complexity and latency decision

| Approach | Extra routing latency/calls | Semantic quality | Operational complexity | Suitable for Pi-Apex now? |
|---|---:|---|---|---|
| Keep current model; use `apex/auto` for plan→implementation | No classifier call; one existing phase switch after first successful write | Understands phase transition, not initial task class | Low | **Yes, recommended baseline** |
| Deterministic local router at submit, among configured profiles | Negligible CPU; no added model/API call | Strong only for explicit cues; brittle on ambiguous natural language | Low–medium (per-request model persistence, test matrix, policy) | **Possible optional experiment**, not a claim of semantic understanding |
| Separate lightweight classifier model at submit | At least one extra model request before work | Better semantic potential; still fallible | Medium–high (classifier config, timeout/failure fallback, privacy, billing, evals) | **Not unless benchmark shows worthwhile gains** |
| Main model invokes a route/delegation tool when needed | Conditional extra model/tool turn | Uses conversation context; not guaranteed to invoke | Medium; routes and tool lifecycle need safety/audit | **Reasonable future opt-in** if delegation is the actual need |
| Hosted router (Cursor/OpenRouter or provider gateway) | Router-specific; exact overhead must be measured | Depends on vendor classifier/model pool | Low client complexity, higher provider/policy dependence | **Only if user accepts external routing/billing/privacy terms** |

## Recommendation

1. **Do not ship an always-on LLM classifier yet.** The user's objective is a useful personal harness, not reproducing Cursor's proprietary router. The likely incremental value is not established, while a classifier call would add a round trip and cost.
2. **Keep `apex/auto` as the no-extra-classifier choice for coding work.** It already routes by phase (planning → implementation). Clarify in UI/docs that it is not per-prompt task classification.
3. **Separate model routing from workflow dispatch.** A model pick can be made at the start of a request among the operator’s allow-listed, already configured models. Browser, multi-agent, and schedule actions should remain explicit or require the relevant existing approvals; a text classifier must not create unattended work or silently spawn teams.
4. **Fix nomenclature:** rename current “Automatic — use the normal prompt” to “Normal prompt — keep current model” (or similar). Reserve “Auto route” for behavior that really classifies the submitted request.
5. If the user wants to evaluate true automatic routing, first make an **opt-in Auto Route experiment** with no additional classifier model: classify only the complete submitted prompt using deterministic rules, switch only among explicit named configured profiles, show route/reason/model in the transcript, and fall back to the selected model on low confidence/error. Measure route accuracy, first-token latency, total cost, and user override rate on representative personal tasks. Do not silently switch credentials or provider keys.
6. Add an LLM classifier only if the local experiment misses important cases *and* a measured quality/cost/latency test beats the baseline. Keep the classifier call optional and visible; never use hidden reasoning as a security boundary.
